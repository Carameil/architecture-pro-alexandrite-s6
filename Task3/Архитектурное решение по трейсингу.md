# Архитектурное решение по трейсингу

## 1. Анализ системы и места для трейсинга

### Критические точки, где заказы могут "сломаться" или зависнуть:

1. **Shop API → MES API** (расчет цены)
   - Запрос на расчет цены 3D модели
   - Может зависнуть на 2-30 минут
   - Потеря запроса = потеря заказа

2. **Shop API ↔ RabbitMQ** (отправка в очереди)
   - Публикация событий о новых заказах
   - Сообщения могут потеряться или не обработаться

3. **RabbitMQ ↔ CRM API** (обработка заказов)
   - Получение заказов из очереди
   - Изменение статусов заказов
   - Сообщения могут зависнуть в очереди

4. **RabbitMQ ↔ MES API** (производственные процессы)
   - Уведомления о готовности к производству
   - Изменения статусов производства
   - Критично для операторов

5. **API ↔ Базы данных** (сохранение данных)
   - Записи о заказах в Shop DB
   - Обновления статусов в MES DB
   - Транзакции могут не завершиться

6. **Внешние API пользователи → MES API**
   - B2B партнеры создают заказы через API
   - Высокая нагрузка, много потерь

### Системы для покрытия трейсингом:
- ✅ Shop API (Spring Boot)
- ✅ CRM API (Spring Boot) 
- ✅ MES API (C#)
- ✅ RabbitMQ (очереди сообщений)
- ✅ PostgreSQL (все базы данных)
- ✅ S3 хранилище (загрузка/чтение 3D файлов)

## 2. Данные для трейсинга

### Обязательные поля для всех спанов:
- **traceId** - уникальный ID всего трейса
- **spanId** - ID конкретного шага
- **parentSpanId** - ID родительского шага
- **orderId** - номер заказа (ключевое поле)
- **customerId** - ID клиента
- **timestamp** - время начала и окончания
- **duration** - длительность операции
- **status** - успех/ошибка
- **service** - название сервиса

### HTTP запросы:
- **method** - GET, POST, PUT
- **url** - полный путь запроса
- **status_code** - 200, 404, 500
- **user_agent** - для анализа клиентов

### RabbitMQ сообщения:
- **queue** - название очереди
- **exchange** - точка обмена
- **routing_key** - ключ маршрутизации
- **message_id** - ID сообщения
- **retry_count** - количество попыток
- **correlation_id** - связь с заказом

### База данных:
- **query_type** - SELECT, INSERT, UPDATE
- **table** - название таблицы
- **rows_affected** - количество строк
- **query_duration** - время выполнения

### Бизнес-события:
- **order_status** - текущий статус заказа
- **price_calculation_result** - результат расчета цены
- **file_size** - размер 3D файла
- **operator_id** - кто обрабатывает заказ

## 3. Мотивация

### Почему нужен трейсинг:

**Проблемы сейчас:**
- Заказы "исчезают" и мы не знаем где
- Клиенты жалуются, но мы не можем найти их заказы
- Потеря крупных B2B контрактов из-за непонятных задержек
- Операторы не понимают, почему заказ не приходит в работу

**Что даст трейсинг:**
- Увидим полный путь каждого заказа от создания до отправки
- Найдем где именно "застревают" заказы
- Сможем быстро отвечать клиентам что происходит с их заказом
- Восстановим доверие B2B партнеров

### Технические метрики, на которые повлияет трейсинг:

1. **MTTR (время восстановления)** - с часов до минут
   - Сейчас: ищем проблему по логам несколько часов
   - Будет: находим проблемный спан за 2-3 минуты

2. **Время диагностики инцидентов** - в 10 раз быстрее
   - Сейчас: опрашиваем все системы, ищем в БД
   - Будет: смотрим трейс и видим где остановился заказ

3. **Процент успешно обработанных заказов** - рост на 15-20%
   - Увидим потерянные заказы и восстановим их
   - Найдем узкие места и оптимизируем

### Бизнес-метрики, на которые повлияет трейсинг:

1. **Customer Satisfaction Score (CSAT)** - рост на 25%
   - Сможем точно отвечать клиентам о статусе заказа
   - Предотвратим потерю заказов

2. **Retention rate B2B партнеров** - рост на 30%
   - Докажем надежность нашей системы
   - Быстро решим проблемы партнеров

3. **Время выполнения заказа** - снижение на 20%
   - Найдем и устраним узкие места
   - Оптимизируем процесс обработки

4. **Выручка** - рост на 10-15%
   - Меньше потерянных заказов
   - Больше довольных клиентов и партнеров

## 4. Предлагаемое решение

### Технологический стек:

**OpenTelemetry** - стандарт для сбора трейсов
- Автоматическая инструментация для Spring Boot
- SDK для C# (MES API)
- Поддержка RabbitMQ и PostgreSQL

**Jaeger** - хранение и визуализация трейсов
- Быстрый поиск по orderId
- Flame graph для анализа производительности
- Web UI для команды поддержки

**OpenTelemetry Collector** - сбор и маршрутизация
- Принимает трейсы от всех сервисов
- Отправляет в Jaeger для хранения
- Экспортирует метрики в Prometheus

### Архитектура решения:

1. **Инструментация сервисов:**
   - Shop API, CRM API: OpenTelemetry Java Agent
   - MES API: OpenTelemetry .NET SDK
   - Автоматический сбор HTTP, DB, RabbitMQ трейсов

2. **Передача trace context:**
   - HTTP заголовки: `traceparent`, `tracestate`
   - RabbitMQ headers: trace ID в сообщениях
   - Correlation ID = orderId для связи с бизнесом

3. **Сбор и хранение:**
   - OTel Collector собирает OTLP данные
   - Jaeger хранит трейсы 14 дней
   - Elasticsearch для долгосрочного хранения (опционально)

### Компоненты для внедрения:

**Новые компоненты (красным на диаграмме):**
- OpenTelemetry Collector
- Jaeger Query Service
- Jaeger UI
- Jaeger Storage (Elasticsearch)

**Доработка существующих:**
- Добавить OTel агенты во все API
- Настроить propagation в RabbitMQ
- Добавить trace ID в логи

### Пример использования:

1. Клиент создает заказ → получаем traceId
2. Заказ отправляется на расчет цены → тот же traceId
3. Расчет идет в MES → продолжение трейса
4. Результат возвращается → завершение трейса
5. В Jaeger видим полный путь заказа за 2-30 минут

## 5. Компромиссы

### Где трейсинг не поможет или будет дорогим:

1. **Старые версии библиотек**
   - Некоторые версии Spring Boot могут не поддерживать автоинструментацию
   - Потребуется обновление зависимостей

2. **Производительность**
   - Трейсинг добавляет 1-3% overhead на CPU
   - Сетевые вызовы для отправки трейсов
   - Решение: sampling (записываем не все трейсы)

3. **Хранение данных**
   - Трейсы занимают много места (GB в день)
   - Elasticsearch требует ресурсов
   - Решение: retention 14 дней, сжатие

4. **Сложность настройки**
   - Нужно настроить propagation между всеми сервисами
   - Отладка проблем с трейсингом может быть сложной
   - Требуется обучение команды

5. **Приватные данные**
   - Трейсы могут содержать персональные данные
   - Нужна осторожность с логированием
   - Решение: data scrubbing, маскирование

### Что не покроем в первой версии:
- Фронтенд трейсы (Vue/React)
- Внешние системы (платежи, доставка)
- Legacy код без возможности изменения

## 6. Безопасность

### Контроль доступа:
- **Аутентификация**: только сотрудники компании с корпоративным SSO
- **Авторизация**: роли "Support", "Developer", "Admin"
- **Сетевая безопасность**: Jaeger UI только во внутренней сети

### Защита данных:
- **Маскирование PII**: автоматически скрываем email, телефоны, адреса
- **Шифрование**: TLS для передачи трейсов
- **Audit log**: логируем кто и что смотрел в Jaeger

### Роли и права:
- **Support**: просмотр трейсов, поиск по orderId
- **Developer**: полный доступ для отладки
- **Admin**: управление retention, конфигурация

### Соответствие требованиям:
- **GDPR**: возможность удаления трейсов по запросу
- **Внутренние политики**: шифрование, аудит доступа
- **Резервное копирование**: только метаданные, без персональных данных

## 7. Дополнительное задание: Автоматический мониторинг и алертинг

### Автоматические проверки заказов:

1. **Order Watchdog Service** (новый компонент)
   - Периодически проверяет Jaeger на "застрявшие" заказы
   - Ищет трейсы без завершения более N минут
   - Отправляет алерты команде

2. **SLA мониторинг**
   - Автоматически считает время обработки заказов
   - Алерт если p95 > 3 недели
   - Дашборд с трендами по времени обработки

3. **Anomaly Detection**
   - Ищет аномалии в длительности операций
   - Алерт если расчет цены > 45 минут
   - Уведомление о всплесках ошибок

### Интеграция с алертингом:

**Новые компоненты (зеленым на диаграмме):**
- Order Watchdog Service
- Trace Analytics Service  
- Alert Manager Integration

**Алерты:**
- Slack уведомления для команды
- Email для критических проблем
- PagerDuty для инцидентов в нерабочее время

**Метрики из трейсов:**
- Среднее время обработки заказа
- Процент успешных заказов  
- Топ самых медленных операций
- Количество застрявших заказов
