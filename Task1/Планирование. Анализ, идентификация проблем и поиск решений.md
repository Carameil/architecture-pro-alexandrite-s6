# Планирование: анализ, идентификация проблем и поиск решений

## 1. Анализ текущей архитектуры

Компания "Александрит" - B2C ювелирный онлайн-магазин с уникальной возможностью загрузки/создания 3D-моделей изделий и B2B API для партнеров. Система включает:
- Онлайн-магазин (Vue + Spring Boot)
- CRM (Vue + Spring Boot)  
- MES (React + C#)
- RabbitMQ для интеграции
- PostgreSQL базы данных
- S3-совместимое хранилище для 3D-файлов

Ключевые ограничения:
- Монолитные сервисы на одиночных EC2 инстансах
- БД с единственным writer/reader инстансом
- Линейный рост нагрузки (+100 заказов/месяц)
- Недавно открытый публичный API привел к резкому росту заказов

## 2. Идентифицированные проблемы

### Критические проблемы производительности и масштабирования:
1. **Единственные инстансы для каждого приложения и БД** - отсутствие горизонтального масштабирования, single point of failure, ресурсное насыщение
2. **Длительный расчет цены в MES (2-30 мин)** - блокирует поток обработки заказов, создает очереди
3. **Проблемы с дашбордом операторов MES** - медленная загрузка первой страницы даже после добавления фильтров и пагинации
4. **Отсутствие кеширования** - каждый запрос идет в БД, создавая избыточную нагрузку
5. **Нет пула соединений и оптимизации БД запросов** - вероятные N+1 проблемы, отсутствующие индексы

### Проблемы надежности и интеграции:
6. **Потеря сообщений в RabbitMQ** - заказы "застревают" между статусами, нет механизмов гарантированной доставки
7. **Отсутствие идемпотентности операций** - риск дублирования заказов и состояний
8. **Нет обработки poison messages и DLQ** - проблемные сообщения блокируют очереди
9. **Отсутствие circuit breakers и retry политик** - каскадные сбои при проблемах с зависимостями

### Проблемы наблюдаемости:
10. **Недостаточный мониторинг** - только Яндекс.Метрика для фронтенда, нет технических метрик
11. **Отсутствие централизованного логирования** - невозможно быстро диагностировать проблемы
12. **Нет distributed tracing** - сложно отследить путь заказа через системы
13. **Отсутствие SLO/SLI и алертинга** - реактивный подход к инцидентам

### Процессные проблемы:
14. **Ручное тестирование как ворота релиза** - задержки до месяца и более
15. **Ручной деплой в release/prod** - риск человеческой ошибки, медленный rollback
16. **Отсутствие автоматизированных E2E тестов** - QA перегружен

### Архитектурные проблемы:
17. **Синхронная обработка долгих операций** - расчет цены блокирует API
18. **Отсутствие rate limiting и backpressure** - публичный API может быть перегружен
19. **Монолитная архитектура сервисов** - сложно масштабировать отдельные компоненты

## 3. Инициативы по устранению проблем

### P0 - Критические (немедленное внедрение):

1. **Внедрение комплексной observability платформы**
   - Prometheus + Grafana для метрик (RED/USE подходы)
   - ELK стек для централизованного логирования
   - OpenTelemetry + Jaeger для distributed tracing
   - Настройка SLO/SLI и алертинга

2. **Стабилизация потоков обработки заказов**
   - Внедрение идемпотентных консьюмеров и Outbox pattern
   - Настройка DLQ и retry политик в RabbitMQ
   - Добавление correlation ID для отслеживания сообщений
   - Circuit breakers для внешних зависимостей

3. **Оптимизация производительности критических путей**
   - Redis кеширование для дашборда операторов и каталога
   - Оптимизация БД запросов (индексы, устранение N+1)
   - HTTP кеширование для статики и стабильных API ответов
   - Connection pooling для БД

### P1 - Высокий приоритет (1-3 месяца):

4. **Миграция на Kubernetes с автомасштабированием**
   - Контейнеризация всех сервисов
   - HPA на основе CPU и custom метрик
   - Graceful shutdown и rolling updates
   - Распределение нагрузки через cloud LB

5. **Асинхронная обработка расчета цен**
   - Выделение воркеров для расчета в отдельный пул
   - Очередь задач для долгих вычислений
   - Прогресс и чекпоинты для восстановления

6. **Масштабирование БД**
   - Read replicas для чтения
   - Партиционирование таблиц заказов
   - Оптимизация slow queries
   - Резервное копирование и disaster recovery

7. **Защита от перегрузок**
   - Rate limiting на API endpoints
   - Backpressure механизмы
   - Приоритизация запросов (B2C vs B2B)
   - Квоты для API партнеров

### P2 - Средний приоритет (3-6 месяцев):

8. **Автоматизация CI/CD**
   - Автоматизированные E2E тесты
   - Progressive deployment (canary, blue-green)
   - Автоматический rollback при проблемах
   - Feature flags для безопасных релизов

9. **Улучшение архитектуры**
   - Выделение pricing service как отдельного микросервиса
   - API Gateway для управления трафиком
   - Event-driven архитектура для статусов заказов
   - CQRS для разделения чтения и записи

10. **Оптимизация хранения**
    - S3 lifecycle policies для 3D файлов
    - CDN для статических ресурсов
    - Архивирование старых заказов

## 4. Целевая архитектура через 6 месяцев

### Инфраструктура:
- **Kubernetes кластер** с автомасштабированием (HPA/VPA)
- **Multi-replica deployment** для всех сервисов
- **PostgreSQL с read replicas** и connection pooling
- **Redis кластер** для кеширования
- **Managed RabbitMQ** с настроенными DLQ и мониторингом

### Сервисы:
- **API Gateway** для управления внешним трафиком
- **Выделенный Pricing Service** с воркерами для расчетов
- **Асинхронная обработка** длительных операций через очереди
- **Circuit breakers и retry** механизмы везде

### Observability:
- **Полный стек мониторинга**: Prometheus + Grafana с дашбордами RED/USE
- **Централизованные логи**: ELK с настроенными индексами и retention
- **Distributed tracing**: OpenTelemetry → Jaeger для всех сервисов
- **Проактивный алертинг** на основе SLO

### Процессы:
- **Автоматизированный CI/CD** с progressive delivery
- **Автотесты** как часть pipeline
- **GitOps** для управления конфигурацией

## 5. Топ-3 инициативы на ближайшие 6 месяцев

Если можно выполнить только три пункта, я выбираю:

### 1. Комплексная observability платформа (Prometheus + ELK + Jaeger)
**Обоснование**: Без видимости невозможно эффективно решать проблемы. Это фундамент для всех последующих улучшений. Позволит:
- Быстро находить узкие места (где теряется время на обработку заказов)
- Отслеживать потерянные заказы через distributed tracing
- Проактивно реагировать на проблемы через алертинг
- Измерять эффект от других инициатив

### 2. Стабилизация обработки заказов (идемпотентность, DLQ, circuit breakers)
**Обоснование**: Напрямую решает критическую бизнес-проблему - потерю заказов и нарушение SLA. Это относительно быстрые изменения с высоким ROI:
- Гарантированная доставка сообщений остановит потерю заказов
- Circuit breakers предотвратят каскадные сбои
- DLQ позволит обрабатывать проблемные заказы отдельно

### 3. Кеширование критических путей (Redis + HTTP cache)
**Обоснование**: Быстрый выигрыш в производительности с минимальными изменениями архитектуры:
- Мгновенное улучшение UX для операторов (критическая боль)
- Снижение нагрузки на БД на 60-80% для read-heavy операций
- Улучшение времени отклика API для партнеров
- Создает запас прочности для дальнейшего роста

Эти три инициативы создают прочный фундамент: видимость проблем → стабильность потоков → быстрая производительность. После их внедрения можно будет безопасно проводить более глубокие архитектурные изменения.
