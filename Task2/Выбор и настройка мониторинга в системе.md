# Выбор и настройка мониторинга в системе

## 1. Мотивация

### Почему компании "Александрит" критически необходим технический мониторинг

В настоящее время компания сталкивается с серьезными проблемами, которые напрямую влияют на бизнес-показатели:

**Финансовые потери:**
- Потеря крупных B2B контрактов из-за нарушения SLA (время обработки заказа > 3 недель вместо обещанных)
- Отток B2C клиентов из-за "потерянных" заказов и долгого ожидания
- Упущенная выручка из-за недоступности сервисов (не можем измерить без мониторинга)

**Операционная слепота:**
- Яндекс.Метрика видит только фронтенд, но не API и внутренние процессы
- Невозможно понять, где именно "застревают" заказы (Shop API? MES? RabbitMQ?)
- Нет данных о том, сколько заказов от API-партнеров успешно обрабатывается
- Операторы жалуются на медленный дашборд, но мы не знаем, насколько медленный

**Реактивный подход вместо проактивного:**
- Узнаем о проблемах только из жалоб клиентов
- Невозможно предсказать и предотвратить инциденты
- Нет данных для обоснования инвестиций в инфраструктуру

### Что даст внедрение мониторинга:

1. **Восстановление доверия клиентов** - SLA compliance, прозрачность статусов заказов
2. **Оптимизация затрат** - понимание, где нужно масштабирование, а где - оптимизация
3. **Ускорение диагностики** - с часов/дней до минут
4. **Обоснованные решения** - данные для приоритизации улучшений
5. **Конкурентное преимущество** - надежность как USP для B2B партнеров

## 2. Выбор подхода к мониторингу

Основываясь на архитектуре системы и типах компонентов, применим комбинированный подход:

### RED метод (Rate, Errors, Duration)
**Применяем для всех API сервисов:**
- Shop API - критичен для B2C и загрузки 3D моделей
- CRM API - управление статусами заказов
- MES API - расчет цен и управление производством

**Обоснование:** RED оптимален для request-driven сервисов, дает быстрое понимание user experience

### USE метод (Utilization, Saturation, Errors)
**Применяем для инфраструктурных компонентов:**
- EC2 инстансы (CPU, Memory, Disk, Network)
- PostgreSQL базы данных (connections, disk space, IOPS)
- RabbitMQ (queue depth, memory, disk)
- S3 хранилище (space, request rate)

**Обоснование:** USE идеален для выявления bottlenecks в ресурсах

### Четыре золотых сигнала (дополнительно)
**Применяем как общий framework для всей системы:**
- Latency - время отклика для всех операций
- Traffic - объем запросов/заказов
- Errors - процент неуспешных операций
- Saturation - загрузка ресурсов

**Обоснование:** Обеспечивает целостное видение системы для SRE практик

## 3. Основные метрики для отслеживания

### 3.1 API сервисы (RED метрики)

#### Для всех API (Shop API, CRM API, MES API):

- **Метрика:** `http_requests_total`
  - **Зачем:** Понимать нагрузку на сервисы - сколько запросов обрабатываем
  - **Ярлыки:** `{service="shop-api|crm-api|mes-api", status="2xx|4xx|5xx"}`

- **Метрика:** `http_request_duration_seconds`
  - **Зачем:** Измерять скорость ответа - насколько быстро работают API
  - **Ярлыки:** `{service="shop-api|crm-api|mes-api"}`

- **Метрика:** `http_errors_total`
  - **Зачем:** Отслеживать ошибки - где и как часто что-то ломается
  - **Ярлыки:** `{service="shop-api|crm-api|mes-api"}`

#### Специальные метрики:

- **Метрика:** `price_calculation_duration_seconds` (только MES API)
  - **Зачем:** Самая важная метрика - время расчета цены влияет на SLA
  - **Ярлыки:** `{complexity="simple|complex"}`

- **Метрика:** `dashboard_load_time_seconds` (только MES API)
  - **Зачем:** Операторы жалуются на медленный дашборд - нужно измерить
  - **Ярлыки:** `{page="orders_list"}`

### 3.2 RabbitMQ (очереди сообщений)

- **Метрика:** `rabbitmq_queue_messages_ready`
  - **Зачем:** Видеть, не накапливаются ли сообщения в очередях
  - **Ярлыки:** `{queue="orders|status_updates"}`

- **Метрика:** `rabbitmq_queue_messages_unacked`
  - **Зачем:** Понимать, не "зависают" ли сообщения при обработке
  - **Ярлыки:** `{queue="orders|status_updates"}`

### 3.3 База данных (PostgreSQL)

- **Метрика:** `pg_connections_active`
  - **Зачем:** Следить, чтобы не закончились соединения к БД
  - **Ярлыки:** `{database="shop|crm|mes"}`

- **Метрика:** `pg_database_size_bytes`
  - **Зачем:** Планировать расширение дискового пространства
  - **Ярлыки:** `{database="shop|crm|mes"}`

### 3.4 Серверы (USE метрики)

- **Метрика:** `node_cpu_usage_percent`
  - **Зачем:** Видеть загрузку процессора - когда нужно добавлять мощности
  - **Ярлыки:** `{instance="shop-server|crm-server|mes-server"}`

- **Метрика:** `node_memory_usage_percent`
  - **Зачем:** Отслеживать использование памяти - предотвращать "падения"
  - **Ярлыки:** `{instance="shop-server|crm-server|mes-server"}`

- **Метрика:** `node_disk_usage_percent`
  - **Зачем:** Не дать диску переполниться
  - **Ярлыки:** `{instance="shop-server|crm-server|mes-server"}`

### 3.5 Бизнес-метрики

- **Метрика:** `orders_created_total`
  - **Зачем:** Отслеживать количество заказов - основной показатель бизнеса
  - **Ярлыки:** `{source="website|api"}`

- **Метрика:** `orders_stuck_total`
  - **Зачем:** Считать "застрявшие" заказы - главная проблема сейчас
  - **Ярлыки:** `{status="SUBMITTED|PRICE_CALCULATED|MANUFACTURING_STARTED"}`

- **Метрика:** `order_processing_time_seconds`
  - **Зачем:** Измерять время от заказа до отправки - соблюдение SLA
  - **Ярлыки:** `{order_type="b2c|b2b"}`

## 4. План действий

### Этап 1 - Настройка инфраструктуры (1-2 недели)
1. **Установить Prometheus и Grafana** в облаке
2. **Поставить базовые экспортеры:**
   - Node Exporter на серверы (для CPU, память, диск)
   - PostgreSQL Exporter для баз данных
   - RabbitMQ Exporter для очередей

### Этап 2 - Добавить метрики в приложения (2-3 недели)
1. **В Spring Boot приложения** (Shop API, CRM API):
   - Подключить Micrometer для автоматических метрик
   - Добавить счетчик заказов и ошибок

2. **В MES API** (C#):
   - Добавить библиотеку prometheus-net
   - Измерять время расчета цен
   - Измерять время загрузки дашборда

### Этап 3 - Создать дашборды (1 неделя)
1. **Основной дашборд** со всеми важными метриками
2. **Настроить простые алерты** на критические проблемы
3. **Написать инструкцию** как пользоваться

## 5. Основные пороговые значения (когда бить тревогу)

### Серверы
- **CPU > 80%** → Предупреждение команде
- **Memory > 85%** → Нужно проверить, не утекает ли память
- **Диск > 90%** → Срочно расширить место

### API
- **Время ответа > 1 секунда** → Что-то тормозит
- **Ошибки > 5%** → Серьезные проблемы
- **Расчет цены > 30 минут** → Критично для бизнеса

### RabbitMQ
- **В очереди > 1000 сообщений** → Накапливается backlog
- **Сообщения не обрабатываются > 10 минут** → Что-то сломалось

### База данных
- **Соединения > 80% от максимума** → Скоро кончатся
- **Размер БД растет > 10GB в день** → Планировать расширение

### Что делать при превышении:
1. **Немедленно** - уведомить команду в чат
2. **В течение часа** - проанализировать причину
3. **В течение дня** - принять меры (перезапуск, масштабирование, оптимизация)

## 6. Что получим в результате

### Через месяц:
- Будем видеть, что происходит в системе
- Сможем быстро находить проблемы
- Поймем, где узкие места

### Через 3 месяца:
- Будем предотвращать проблемы до того, как они случатся
- Клиенты перестанут жаловаться на потерянные заказы
- Операторы получат быстрый дашборд

### Через полгода:
- Система станет стабильной и предсказуемой
- Сможем планировать развитие на основе данных
- Вернем доверие B2B партнеров

## 7. Стоимость и выгода

### Сколько потратим:
- Сервера для мониторинга: ~30 000 ₽/месяц
- Время на настройку: 1 месяц одного разработчика
- Поддержка: несколько часов в неделю

### Что получим взамен:
- Не потеряем крупных клиентов = экономия миллионов рублей
- Быстрее будем находить проблемы = экономия времени команды
- Оптимизируем серверы = экономия на железе

**Вывод:** Мониторинг быстро окупается и помогает бизнесу расти.
