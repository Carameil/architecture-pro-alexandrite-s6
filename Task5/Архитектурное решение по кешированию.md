# Архитектурное решение по кешированию

## 1. Анализ системы и определение областей для кеширования

### Анализ текущих проблем производительности:

**MES API (критический компонент):**
- Дашборд операторов загружается медленно даже после добавления фильтров и пагинации
- Операторы должны видеть самые новые заказы для получения вознаграждения
- Вероятные причины: N+1 запросы, отсутствие индексов, тяжелые агрегации
- Read-heavy нагрузка — идеальный кандидат для кеширования

**Shop API (высокая нагрузка):**
- Каталог товаров и статические данные
- Информация о статусах заказов для клиентов
- Public API для B2B партнеров с возросшей нагрузкой

**Области для кеширования:**

1. **MES дашборд операторов** (серверное кеширование)
   - Список заказов по статусам
   - Агрегированная статистика
   - Детали заказов для быстрого просмотра

2. **Shop API responses** (HTTP кеширование)
   - Каталог товаров
   - Статические ресурсы (изображения, JS, CSS)
   - Стабильные API endpoints

3. **Частые DB запросы** (серверное кеширование)
   - Справочники и каталоги
   - Пользовательские сессии
   - Результаты расчетов цен (где возможно)

## 2. Мотивация

### Текущие проблемы:

**Операционные проблемы:**
- Операторы тратят 30-60 секунд на загрузку дашборда → снижение производительности
- Каждый клик по фильтру = новый тяжелый запрос к БД
- БД перегружена read-запросами, особенно в часы пик
- API партнеры жалуются на медленные ответы

**Бизнес-воздействие:**
- Операторы не успевают обрабатывать заказы → нарушение SLA
- Потеря B2B контрактов из-за медленного API
- Повышенная нагрузка на инфраструктуру → дополнительные расходы

### Что даст внедрение кеширования:

**Немедленные улучшения производительности:**
- Время загрузки дашборда MES: с 30-60 сек до 2-5 сек (10-15x ускорение)
- Время ответа API endpoints: с 500-2000ms до 50-200ms (5-10x ускорение)
- Снижение нагрузки на PostgreSQL на 60-80% для read операций

**Бизнес-метрики:**
- Повышение производительности операторов на 25-30%
- Улучшение user experience для B2B партнеров
- Снижение затрат на инфраструктуру БД
- Создание запаса прочности для дальнейшего роста

**Технические метрики:**
- DB connections utilization: снижение с 80% до 30-40%
- p95 latency MES dashboard: с 30s до 3s
- Cache hit ratio: целевой показатель 85-90%

## 3. Предлагаемое решение

### Серверное кеширование (Redis) — основное решение

**Выбор: комбинация Cache-Aside + Write-Through + Refresh-Ahead**

#### Cache-Aside для дашборда операторов:
**Зачем:** Простота реализации, устойчивость к сбоям кеша
**Как работает:**
1. Приложение проверяет кеш
2. При cache miss → запрос к БД → сохранение в кеш
3. При cache hit → возврат данных из кеша

**Почему Cache-Aside:**
- ✅ Простая логика в коде
- ✅ Система работает даже если Redis недоступен
- ✅ Гибкость в управлении ключами
- ❌ Первый запрос всегда медленный (cold cache)

**Альтернативы и почему не подходят:**
- **Read-Through:** усложняет архитектуру, кеш становится single point of failure
- **Write-Behind:** риск потери данных, не подходит для критичных операций

#### Write-Through для изменений статусов:
**Зачем:** Операторы должны видеть актуальные данные немедленно
**Как работает:**
1. Запись идет одновременно в БД и кеш
2. Операция считается завершенной только после записи в оба хранилища
3. Консистентность данных гарантирована

**Почему Write-Through:**
- ✅ Гарантированная консистентность данных
- ✅ Операторы видят изменения мгновенно
- ✅ Простая логика обновления
- ❌ Немного медленнее записи

#### Refresh-Ahead для горячих данных:
**Зачем:** Скрыть latency БД для часто запрашиваемых данных
**Как работает:**
1. Фоновый процесс обновляет популярные ключи до истечения TTL
2. Пользователи всегда получают свежие данные из кеша
3. БД нагружается равномерно, без всплесков

### HTTP кеширование — дополнительное решение

**Static assets:**
```http
Cache-Control: public, max-age=31536000, immutable
```

**API responses (стабильные данные):**
```http
Cache-Control: private, max-age=300
ETag: "abc123"
```

**API responses (изменяемые данные):**
```http
Cache-Control: private, no-cache
ETag: "def456"
If-None-Match: "def456" → 304 Not Modified
```

### Архитектура кеширования:

**Redis кластер:**
- 3 ноды (master + 2 replicas)
- Persistence отключена (кеш может быть восстановлен из БД)
- Memory: 16-32 GB на начальном этапе

**Ключи кеша:**
```
mes:dashboard:orders:newest:v1          → последние 200 заказов
mes:dashboard:orders:status:{status}:v1 → заказы по статусу
mes:dashboard:stats:v1                  → общая статистика
mes:order:{orderId}:v1                  → детали заказа
shop:catalog:products:v1                → каталог товаров
```

**TTL стратегия:**
- Dashboard списки: 30 секунд
- Детали заказов: 2 минуты
- Каталог товаров: 1 час
- Статистика: 5 минут

## 4. Диаграммы последовательности

**Ссылка на интерактивные диаграммы:** [sequence-diagrams.drawio](sequence-diagrams.drawio)

### A) Чтение списка заказов (Cache-Aside)

1. **Cache Hit сценарий:**
   - MES UI → MES API: GET /dashboard?status=MANUFACTURING_STARTED
   - MES API → Redis: GET cached orders list
   - Redis → MES API: данные из кеша (быстро!)
   - MES API → MES UI: 200 OK (2-3 секунды)

2. **Cache Miss сценарий:**
   - MES UI → MES API: GET /dashboard
   - MES API → Redis: GET cached orders (не найдено)
   - MES API → PostgreSQL: SELECT тяжелый запрос (медленно)
   - PostgreSQL → MES API: данные из БД
   - MES API → Redis: SET cache для следующего раза
   - MES API → MES UI: 200 OK (30-60 секунд)

### B) Изменение статуса заказа (Write-Through)

1. MES UI → MES API: POST /orders/123/status (изменить статус)
2. MES API → PostgreSQL: UPDATE orders (запись в БД)
3. MES API → Redis: SET обновленные данные заказа
4. MES API → Redis: DEL списки заказов (инвалидация)
5. MES API → RabbitMQ: уведомление об изменении
6. MES API → MES UI: 200 OK (данные консистентны)

**Результат:** Операторы сразу видят изменения, кеш остается актуальным

## 5. Стратегия инвалидации кеша

### Комбинированный подход:

#### Программная инвалидация (основная):
**Применение:** Изменения статусов заказов, обновления данных
**Механизм:**
- При изменении заказа удаляем все связанные ключи
- Используем паттерны ключей для групповых операций
- Event-driven подход через RabbitMQ для синхронизации

**Преимущества:**
- ✅ Мгновенное отражение изменений
- ✅ Консистентность данных
- ✅ Контролируемая инвалидация

#### Временная инвалидация (TTL) как safety net:
**Применение:** Автоматическая очистка всех ключей
**Настройки:**
- Короткие TTL для динамических данных (30s-2min)
- Средние TTL для относительно стабильных данных (5-15min)
- Длинные TTL для статических данных (1-24 hours)

**Преимущества:**
- ✅ Защита от "протухших" данных
- ✅ Автоматическая очистка при сбоях
- ✅ Простота эксплуатации

#### По ключу (селективная):
**Применение:** Специфические обновления, массовые операции
**Механизм:**
- Удаление по паттернам: `DEL mes:dashboard:*`
- Prefix-based инвалидация для связанных данных

### Сравнение стратегий инвалидации:

| Стратегия | Преимущества | Недостатки | Подходит для |
|-----------|--------------|------------|--------------|
| **Временная (TTL)** | Простота, автоматичность, защита от stale data | Может показывать устаревшие данные до истечения TTL | Статические данные, safety net |
| **Программная** | Мгновенные обновления, полный контроль | Сложность логики, риск забыть инвалидировать | Критичные данные статусов |
| **По ключу** | Гибкость, точечные обновления | Может быть медленной для больших наборов | Массовые операции |
| **Event-driven** | Loose coupling, масштабируемость | Сложность архитектуры, eventual consistency | Распределенные системы |

**Выбранная комбинация:** Программная + Временная
- Программная для критичных изменений (статусы заказов)
- TTL как страховка и для менее критичных данных

## 6. Ключевые design решения

### Redis конфигурация:
```redis
# Основные настройки
maxmemory 16gb
maxmemory-policy allkeys-lru
save ""  # отключаем persistence для кеша

# Производительность
tcp-keepalive 60
timeout 0
```

### Ключи и пространства имен:
```
Схема: {service}:{entity}:{identifier}:{version}

mes:orders:newest:v1                    # Top 200 новых заказов
mes:orders:status:MANUFACTURING_STARTED:v1  # Заказы по статусу
mes:order:123:v1                        # Конкретный заказ
mes:stats:counts:v1                     # Счетчики по статусам
shop:products:category:rings:v1         # Товары по категории
shop:order:456:status:v1                # Статус заказа для клиента
```

### Cache warming стратегия:
- Preload популярных данных при старте приложения
- Фоновое обновление топ-10 самых используемых ключей
- Мониторинг hit ratio и автоматическая оптимизация TTL
