# Архитектурное решение по логированию

## 1. Какие системы нужно покрыть логированием

### Самые важные (начинаем с них):
- **MES API** — здесь рассчитываются цены, операторы жалуются на медленную работу
- **Shop API** — сюда приходят все заказы от клиентов и API партнеров
- **RabbitMQ** — тут теряются сообщения между системами

### Потом добавим:
- **CRM API** — управление заказами
- **Базы данных** — медленные запросы

## 2. Что логировать (уровень INFO)

### MES API:
- **Расчет цены заказа**: время, номер заказа, сколько заняло времени, какая цена получилась
- **Изменение статуса**: время, номер заказа, старый статус → новый статус, кто изменил
- **Загрузка дашборда**: время, кто открыл, сколько заказов показалось, как долго грузилось

### Shop API:
- **Новый заказ**: время, номер заказа, ID клиента, сумма заказа
- **Загрузка 3D файла**: время, номер заказа, размер файла, успешно ли загрузилось
- **Отправка заказа в работу**: время, номер заказа, статус изменился с INITIATED на SUBMITTED

### CRM API:
- **Одобрение заказа**: время, номер заказа, кто одобрил
- **Закрытие заказа**: время, номер заказа, почему закрыли

### RabbitMQ:
- **Отправка сообщения**: время, в какую очередь, номер заказа
- **Получение сообщения**: время, из какой очереди, номер заказа, успешно ли обработалось

### Другие уровни:
- **WARN** — что-то работает медленно или странно (файл слишком большой, много попыток)
- **ERROR** — что-то сломалось (заказ не обработался, база недоступна)
- **FATAL** — сервис полностью упал

## 3. Мотивация

### Проблемы сейчас:
- Узнаем о проблемах только когда клиенты жалуются
- Долго ищем, где именно сломалось (часами копаемся в файлах на серверах)
- Не понимаем, что происходило с заказом до того, как он "потерялся"
- Команда поддержки перегружена разбором каждого инцидента

### Что даст логирование компании:

**Технические улучшения:**
1. **Быстрое решение проблем** — с часов до минут
   - Поиск по номеру заказа покажет всю историю
2. **Понимание, где тормозит система** 
   - Увидим, что дашборд MES загружается 30 секунд
3. **Автоматические уведомления о проблемах**
   - Система сама скажет, если что-то сломалось

**Бизнес-выгоды:**
1. **Довольные клиенты** — быстро отвечаем на вопросы о заказах
2. **Меньше потерянных заказов** — видим и исправляем проблемы
3. **Экономия времени команды** — не нужно часами искать причины
4. **Лучшее качество релизов** — сразу видим, если что-то сломали

## 4. Какие системы делать первыми

### Сначала (самое важное):
- **MES API** — операторы жалуются, что медленно работает
- **Shop API** — все заказы идут через него

### Потом:
- **RabbitMQ** — чтобы понять, где теряются сообщения
- **CRM API** — для полной картины

**Почему именно так:** MES и Shop API — это то, где сейчас больше всего проблем. Начнем с них, получим быстрый результат.

## 5. Предлагаемое решение

### Выбираем технологии: ELK Stack

**Что это:**
- **Elasticsearch** — база данных для поиска по логам
- **Logstash** — собирает логи с серверов
- **Kibana** — веб-интерфейс для просмотра логов

**Как будет работать:**
1. Каждый сервис пишет логи в файлы
2. Logstash читает эти файлы и отправляет в Elasticsearch
3. В Kibana можем искать логи по номеру заказа или времени

### Пример лога:
```
2025-01-15 10:30:45 INFO [MES-API] Заказ ORD-123: расчет цены начат, файл 3D модели 15MB, полигонов: 50000
2025-01-15 10:33:12 INFO [MES-API] Заказ ORD-123: расчет завершен, цена: 25000 руб, время: 2м 27с
```

### Что нужно установить:
- Сервер Elasticsearch для хранения логов
- Logstash на каждом сервере приложений
- Kibana для просмотра логов
- Настроить приложения, чтобы писали структурированные логи

## 7. Алертинг и поиск проблем

### Простые уведомления:
- **Много ошибок** (больше 10 в минуту) → сообщение в Slack
- **Сервис не отвечает** (нет логов 5 минут) → звонок дежурному
- **Заказы зависают** (расчет цены больше 45 минут) → уведомление команде

### Поиск аномалий:
- **Слишком много заказов за раз** — возможно DDoS атака
  - Обычно: 4 заказа в минуту
  - Странно: 10000 заказов в минуту
- **Новые типы ошибок** после релиза — возможно что-то сломали
- **Резко выросло время обработки** — проблемы с производительностью

### Полезные дашборды:
- **Для операторов**: сколько заказов в работе, какие проблемы
- **Для разработчиков**: где больше всего ошибок, что работает медленно
- **Для руководства**: общая статистика, соблюдение SLA

## 8. Дополнительное задание: Сравнение технологий

| Критерий | ELK | OpenSearch | Splunk | Grafana Loki |
|----------|-----|------------|--------|--------------|
| **Лицензия** | Elastic License (есть ограничения) | Apache License 2.0 (свободная) | Проприетарная (платная) | Apache 2.0 (свободная) |
| **Стоимость** | Средняя (базовая версия бесплатная) | Низкая (полностью бесплатная) | Высокая (от $5000/месяц) | Низкая (бесплатная) |
| **Простота настройки** | Средняя (нужно настроить 3 компонента) | Средняя (как ELK) | Высокая (готовое решение) | Высокая (один компонент) |
| **Поиск по логам** | Отличный (мощные запросы) | Отличный (как Elasticsearch) | Отличный (свой язык SPL) | Хороший (LogQL) |
| **Популярность** | Очень высокая | Средняя (новая) | Высокая | Растущая |

### Мой выбор: **ELK Stack**

**Почему:**
1. **Много примеров** в интернете — легко найти решение проблем
2. **Знают разработчики** — есть опыт в команде или легко найти людей
3. **Хорошая функциональность** — мощный поиск и красивые дашборды
4. **Можно начать бесплатно** — базовая версия покроет наши потребности
5. **Легко масштабировать** — если логов станет много, добавим серверов

**Если бюджет ограничен:** можно попробовать **Grafana Loki** — проще в эксплуатации и полностью бесплатная.
